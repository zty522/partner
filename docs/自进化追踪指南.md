# Partner 自进化追踪：注意事项与验收标准总结

> 目的：在让 Partner 5 实例自己围绕各自任务自进化之前，先明确**根问题**与**追踪标准**。
> 本文档是追踪 Partner 自进化的"标尺"——看到问题后先对照本清单，再判断是否真正解决。

---

## 一、核心原则（最高优先）

1. **一切以"实际效果"为准，流程标志一律不可信**。
   - "步骤 ✅"、"event ok"、"文件存在"、"日志显示成功" 都不是通过依据。
   - 唯一通过依据：**可见产物经得起独立核查**（截图用 read_image 复核内容、代码看真实运行输出、报告看内容是否真实结果）。
2. **让 Partner 自己检测、自己修复**。追踪者（我）的职责是：
   - 观察 → 记录证据 → 判断是否真实现 → **不直接改代码**；
   - 除非自进化确实无法发现/修复，才考虑介入，且介入前先向用户说明。
3. **失败不等待，进入下一轮**。同一策略失败（尤其超时/空白）时，必须反思换策略（滚动/等待/换 URL/执行 JS/换工具），而不是无限重试同一动作。

## 二、根本问题清单：假通过的形态（必须盯住这些）

历史反复出现的问题是：**截图是空的/结果是假的，但被当成"测试通过"**。以下每种形态都曾实际发生过：

| # | 假通过形态 | 真实案例 | 如何识破 |
|---|-----------|---------|---------|
| 1 | **截图是 markdown 文本冒充 png** | files/outgoing 多个 .png 实为 `# 总设计` 文本 | 文件魔数校验（PNG 头）、PIL 打开失败 |
| 2 | **真 PNG 但内容纯白/空白** | 小红书 creation_center.png 纯白（Edge 截登录墙/未渲染） | read_image 描述"空白/无内容" |
| 3 | **真 PNG 但是错误页/登录墙/反爬页** | DDG 错误页 "If this persists..."、Bing 被反爬空白 | read_image 描述内容并对照任务目标 |
| 4 | **步骤失败但日志显示 ✅** | progress_done 固定 ✅ 模板；web_capture 静默失败 | 看步骤 result.ok 与 journal 实际错误 |
| 5 | **命令失败但报告说成功** | run_command `python` not found（exit 127）报告却"已完成" | code_runs.jsonl 的 exit_code/ok |
| 6 | **文件存在但内容是 design 模板** | report.md/api_stats.md/sum_result.md 全是 `# 总设计` | 文件开头是否为 `# 总设计`/占位内容 |
| 7 | **数字"正确"但过程是假的** | sum_result.md 写 5050 但脚本从未运行成功 | 对照 code_runs 记录与脚本实际输出 |
| 8 | **生成代码含未定义变量/假路径** | execute_code 的 `workspace_path` 未定义 → FileNotFoundError | 看 execute_code 步骤 result + stderr |

**追踪时的第一问永远是**：截图内容真的对了吗？代码真的跑出这个结果了吗？报告内容真的对应实际执行了吗？

## 二·五、执行链路真实性验证（消息→读取→执行→效果 全链路）

**追踪时除了看产物，还必须验证"真的执行了"这条链：**

1. **消息真的发到实例了吗**：inbox 有消息（带唯一 id）→ poller 真的读取消费（消息从 inbox 消失/标记）→ 实例对话日志出现"收到指令"
   - 证据：desktop_inbox.jsonl 内容 + dialogue 日志的"收到指令「...」"
2. **代码真的运行了吗**（不是只写了代码/只写了计划）：
   - [ ] 有 create_file/write 写出脚本文件
   - [ ] 有 run_command/execute_code 执行步骤，且 **code_runs.jsonl 有对应记录**（ts/exit_code/stdout）
   - [ ] 执行结果真的被使用（结果写进了报告/产物，不是凭空生成）
3. **实例对话完整达到效果了吗**（一轮对话从头到尾）：
   - 收到指令 → 规划 → 每一步真实执行（步骤 result 有 ok/error）→ 产物生成 → 反思
   - **对话不是"理论上写了计划但没实际做"**：计划步骤必须逐一有执行记录，禁止"计划 9 步但只执行 2 步就报完成"
4. **是否围绕最初用户指令顺利推进**：
   - 意图理解（understand_intent）的目标 = 用户指令核心
   - 每一轮的执行都朝向该目标（换策略是手段，目标不变）
   - 跑偏检测：产物与初始指令无关（如报告内容与任务无关）→ 记为"跑偏"
5. **不是理论上写计划但没执行**（最核心的反模式）：
   - 反模式信号：计划文档很完整但步骤 result 缺失/失败却宣称完成；报告内容引用不存在的执行；"方案落地"类任务只有方案没有运行记录
   - 验证：任务目录 _step_*.result.json 覆盖计划步骤数，且关键步骤 ok=True 有真实产出

## 三、真实效果验收标准（可操作清单）

任何一轮执行，必须逐项验证：

### 1. 截图类产物
- [ ] 文件是真实图片（魔数/PIL 可打开）
- [ ] **read_image 复核内容非空白、非错误页、非登录墙**，且内容与任务目标相关
- [ ] 若内容异常（空白/错误页），下一轮必须换策略，不能接受现状

### 2. 代码运行类
- [ ] code_runs.jsonl 有对应记录（exit_code=0、stdout 真实）
- [ ] 输出结果与任务要求一致（可对照真实数据/预期值）
- [ ] 失败有真实错误信息，且下一轮修复

### 3. 报告/文档类
- [ ] 内容不是 `# 总设计` 开头（design 串写防护应触发）
- [ ] 内容对应实际执行结果（引用了真实文件/输出/截图描述）

### 4. 迭代闭环类
- [ ] 有 intent.md（意图理解：目标/成功标准/期望效果）
- [ ] 有 plan_N.md（本轮计划）
- [ ] 有 reflect_N.md（严格反思：verdict + 证据 + 根因 + 缺口 + 改进）
- [ ] 失败轮次有 next_iteration 启动下一轮（inbox 出现迭代消息），且下一轮策略与上轮反思的改进一致

---

## 四、迭代闭环要求（"进入下一轮而不是等待"）

- 事件链：`understand_intent → write_plan → (执行) → strict_reflect → next_iteration → 新一轮`
- 失败/空白/超时后**必须反思换策略**，禁止：
  - 同一动作无限重试（web_capture 3+ 次超时仍重试）
  - 接受空白截图/错误页作为"完成"
  - 报告写"完成"但产物无效
- 每轮反思要写清楚：**证据（引用了什么）、根因、缺口（能力/工具/策略）、下一轮具体改进**。

## 五、自进化分工

| 角色 | 职责 |
|------|------|
| Partner 实例 | 自己执行任务 → 自己反思 → 自己识别缺口 → 自己规划补齐 → 自己启动下一轮 → **自己修复发现的问题（改 partner 代码）** |
| 追踪者（我/hermes） | 持续观察 5 实例与自进化 → 用本文档标准核查证据 → 记录问题与是否被自进化修复 → 向用户汇报。**只负责 partner 的自进化代码本身**（evolution/ 模块、迭代引擎事件、自进化机制），业务代码修复由 Partner 自进化完成，我不直接改 |
| 用户 | 审核标准与重大决策 |

**分工红线**：
- 实例运行出问题 → 记录证据 → 观察 Partner 自进化是否自己发现并修复（改自己的代码）
- Hermes 不改 executor/browser/planner 等业务代码（除非自进化机制本身有 bug）
- Hermes 的代码改动范围：自进化机制（evolution/、迭代事件、评估/反思/缺口检测/补缺）

**追踪节奏**：周期检查各实例的 iterations/ 目录、任务目录产物、code_runs、journal；发现问题先记录"未修复"，观察后续轮次是否自行解决；若自进化反复不解决同一根问题，向用户报告并给出选项。

## 六、环境与工程注意事项（历史踩坑，追踪时作为背景）

### 浏览器自动化
- 实例主进程 spawn chromium 必 SIGTRAP → 必须 systemd-run 干净进程 + unix socket 长驻（已修复）
- 会话跨进程断裂（open 后 type/click 无页面）→ 长驻 worker 复用（已修复）
- 反爬：headless 特征被识别（UA/plugins/webdriver）→ stealth 注入（已加，待验证效果）
- Bing 新版首页无传统搜索框；DDG html 版返回错误页；小红书/抖音强反爬（登录墙/滑块）
- 页面加载慢：open 后需等待渲染，操作超时 30s
- selector 盲猜：失败时返回可见元素 dump（LLM 据此调整，需验证是否真的会利用）

### 内容质量
- **design 串写是反复出现的高频问题**：LLM 生成"报告"内容就是 `# 总设计` 模板。
  防护：atomic_write_artifact 检测 design 内容 → 替换为依赖步骤实际产出（read_image 描述/execute_code stdout）
- 文件验收 pattern 已兼容 jpg/jpeg/webp/gif

### 运行环境
- NTFS（/mnt/e）：Hermes 工具层 write_file 超时/整写丢数据 → 用 execute_code + cp 或 append
- 实例 systemd 服务 PATH 无 miniconda → `python` 不存在（run_command 已做 python→python3 兼容）
- 改代码后必须清 pyc + 重启实例，否则旧代码生效（NTFS mtime 秒级精度坑）
- 模型分流：普通对话 v4-flash；长生成（batch_plan/action/report）deepseek-chat max_tokens 16000；看图 qwen3-vl-flash
- inbox 消息必须带唯一 `id` 字段（poller 要求）
- 实例级日志：code_runs.jsonl 在 `instances/0X/state/logs/`；迭代状态在 `instances/0X/state/iterations/`
