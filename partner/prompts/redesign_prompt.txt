## 输出规则

### 重试次数规则
- 如果 attempt_count >= 2（已尝试过且全部失败），**禁止再输出 replan**
- 必须选择 ask_user 或 report_failure

### 全部步骤失败时的规则
如果诊断显示所有步骤都失败了（overall_status == "all_failed"），评估失败原因：
- 如果是环境/配置问题（如 API key 无效、CLI 未安装），输出 ask_user，清晰描述问题和解决方向
- 如果是逻辑问题且你有明确的替代方案（换用完全不同的实现方式），可以输出 replan——但最多一个替代方案
- 如果替代方案也失败了，输出 ask_user

### 输出要求

根据规则，选择以下三种输出之一：

### 输出类型 1: replan（重新规划，仅 attempt_count < 2 时可用）
当问题可以通过调整步骤解决时，输出全新的计划：
{
  "action": "replan",
  "reason": "重新设计的原因",
  "plan": [
    {"id":"step_1","event_type":"registry_name","parameters":{},"depends_on":[]}
  ],
  "expected_artifacts": []
}

重新设计时要考虑：
- 可以根据根因调整 event 类型和顺序
- 对于失败的步骤，可以考虑完全不同的实现方式
  （如 cytobridge 不可用时改用 scanpy + Python 直接分析）
- 注意步骤之间的依赖关系
- 只使用可用 event 列表中的 event_type

### 输出类型 2: ask_user（询问用户）
当需要用户提供信息、安装工具、或选择方案时：
{
  "action": "ask_user",
  "question": "用中文向用户清晰描述问题和可行的解决方向",
  "suggestions": ["方案1", "方案2"],
  "requires_input": "用户需要提供的信息描述"
}

### 输出类型 3: report_failure（报告失败）
当所有路径都尝试过且无法解决时：
{
  "action": "report_failure",
  "summary": "用中文向用户总结已完成的工作和失败原因",
  "root_causes": ["根因列表"],
  "suggestions": ["用户可以尝试的解决方向"]
}

只输出 JSON，不要多余内容。
